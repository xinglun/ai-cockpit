# Human Benefit Report

## What this helps you do

Use this report when a person needs a short, evidence-backed answer: what was
completed, what problems were found, what stopped, what was resolved, what
risks remain, what is unknown, and what the safest next action is. It is the
human-facing projection of a validated `OutcomeV2`, not a second authority
source.

## Ask an Agent for the handoff

The repository-bound CLI route is:

```sh
ai-cockpit work-item outcome --repo <repository> --id <work-item-id>
```

An Agent using MCP should call `work_item_outcome` with the repository context
and pass its `humanHandoff` content to the person. `finish`, `archive`, and
`close` also keep lifecycle JSON on stdout and render the same handoff on
stderr by default. A host such as Cursor cannot be forced by the CLI to expand
its chat panel; the Agent or provider adapter must surface the handoff or
replay `work-item outcome`.

The Runtime localizes generated labels, status, unknowns, decisions, and next
actions. Contract intent and acceptance criteria remain in their authored
language and are never machine-translated into governance facts. An
undeclared user benefit remains an explicit unknown; this page does not claim
the reference-only `implementation_approach_report` capability.

For automation, add `--json` to obtain the stable machine-readable `OutcomeV2`
and optional `taskOutcomeReport`. That mode intentionally suppresses the human
handoff; it does not change the underlying facts or authorize a transition.

## What the result contains

The human handoff is decision-oriented and keeps this order:

```text
Task Result
Status: Success / Partial / Blocked / Failed

What was completed
Problems found
Stops triggered
Problems resolved
Risks avoided
Remaining risks
Unknowns
Human decisions
Verification
Impact
Next action
```

Counts are evidence-record counts for findings, warnings, risks, and forced
stops. They are not productivity, time, money, security, or trust scores.
Green requires current Contract/Summary/evidence bindings and verified Runtime
facts; yellow requests investigation or confirmation; red stops a required
control. A short report is never permission to skip review.

## Example

If a missing documentation link was added, a valid handoff can say:

```text
Completed: the missing capability-overview link was added.
Resolved problem: the docs entry now reaches the capability overview.
Evidence: Contract, changed file, and passing documentation-link check.
Remaining risk: Hosted provider review has not yet been confirmed.
Next action: review the PR and wait for the provider result before merge.
```

The Runtime must label unsupported benefit as `unknown` or `inference`; an
Agent must not turn prose into a completed fact. Contract, evidence, and
decision bytes are generated by the Runtime and must not be hand-edited.

## Missing, stale, or invalid reports

Stop and validate the source Outcome when the report is missing, malformed,
stale, cross-task, foreign to the repository, contradictory, or inconsistent
with an archived Outcome. Repair the Contract/evidence through the Runtime and
regenerate the projection; do not edit a report to make it look complete.
Historical evidence remains historical and must not be presented as a current
verification pass or failure.

## Lifecycle and responsibility boundary

The report is produced from the repository-local `.ai/` records across the
explicit lifecycle:

```text
start → preflight → checkpoint → verify → finish → archive → close
```

`work-item outcome` is the official replay route for an Agent or person.
`work_item_get` is a machine-oriented lookup and is not a substitute for the
human handoff. The Runtime owns facts, validation, and localization; the
provider/Agent owns conversation presentation. PR creation, hosted CI, merge,
branch cleanup, platform isolation, enterprise compliance, and production
safety are not proved by this report unless separately bound external
evidence exists.
