# WI-40 — 发布后 Adopter 验收基线

## 意图与目标

只使用不可变公开 Release 制品，建立可重复的发布后 adopter 验收基线。必须证明真实 GitHub
Release 二进制可以从零治理全新的 adopter repository，并在验收失败时保留可审计回执。

## 范围与范围外

范围内：`tests/release/adopter_acceptance.sh`；公开 Release 下载与 digest 校验；隔离的 HOME/XDG/TMP/Cargo/adopter；
attach/profile/Agent/doctor/verify 证据；`first-adopter-smoke` 的 not-ready 断言；完整 Work Item lifecycle；前后 evidence reuse；
`acceptance.json`；目录 `SHA256SUMS`；发布后的 `adopter_acceptance` CI；以及中英日文档。

范围外：Runtime `acceptance` 命令、源码或 Protocol 改动、全局 Agent/MCP 配置、发布前 gate、修改既有 Release truth、第二技术栈 adopter。

## 硬约束

- harness 不使用 `cargo build`、`cargo run`、workspace binary 或本地 `target` binary 获取 AI Cockpit。
- 每次 Runtime 调用都使用下载 binary 的绝对路径，并与 `runtime.json` digest 一致。
- `runtime.json` 绑定 tag、version、archive digest、binary digest、platform、archive、download source 和公开 Release 状态。
- adopter 失败时 `acceptance.json` 保留 `releasePublished: true`；失败回执不能授权后续版本。
- `SHA256SUMS` 覆盖除自身以外的全部 evidence 文件。
- 每次运行使用独立 HOME、XDG_CONFIG_HOME、TMPDIR、CARGO_HOME 和 adopter repository。
- `first-adopter-smoke` 必须保持 `not_ready`，不能伪造 intent、scope、acceptance criteria 或 authority。

## 验收标准

1. 只下载指定公开 Release 的 archive、manifest、checksum，任何 tag/version/digest 不一致或源码 fallback 都失败。
2. Runtime version/binary digest 与 `runtime.json`、doctor、inspect、Work Item verification 一致。
3. 全新 adopter 具有独立 repositoryId，并通过 attach、profile confirm、Agent adapter install 和 `VERIFIED` doctor。
4. `first-adopter-smoke` contract 保持 `not_ready`，人类字段为空或 `unknown`。
5. 独立 Work Item 产出 start、checkpoint、preflight、verify、finish、archive、close、outcome 和 verification 证据。
6. 相同隔离环境的两次 verify 显示第一次执行、第二次 receipt reuse，且第二次 spawn 为零。
7. 源 checkout 没有 `.ai/`，HOME/XDG 前后 manifest 相同。
8. `acceptance.json` 汇总所有步骤，`SHA256SUMS` 绑定完整 evidence 目录。
9. release workflow 只在 `publish` 和 `publish_handoff` 之后运行 harness，成功和失败都上传 evidence，绝不重写已发布 Release。
10. 中英日文档描述相同的发布后边界。

## 所需证据

验收 artifact 必须包含 release/runtime/repository、attach、profile、Agent、verify、isolation JSON，not-ready contract，全部 lifecycle receipt，
`acceptance.json` 和 `SHA256SUMS`。
