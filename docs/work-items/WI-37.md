# WI-37 — Shared Runtime and Repository Context Isolation

## Intent and Goal

Make the Rust Core an external, machine-shared Runtime. A repository is bound
only by an explicit request context; Contracts, evidence, knowledge, and
profiles remain repository-owned and isolated.

## Scope and Out of Scope

In scope: attach-stable `repositoryId`; explicit `--repo` documentation and
request-bound diagrams; move regression coverage; package-test isolation in
hosted CI. Out of scope: changing `cockpit.toml` to JSON, copying Runtime code
into repositories, global active-repository state, Agent provider adapters, or
public release publication.

## Sources and Unknowns

Sources: approved shared-Runtime/three-layer design; Repository Protocol v1;
current Rust CLI, repository service, and Runtime topology documentation.

Known: the CLI and MCP already receive repository paths per request; attach
previously derived the identity from an absolute path. Unknowns owned by the
next Agent Discovery Work Item: provider-specific manifests, managed adapter
ownership, and MCP client discovery.

## Acceptance Criteria

1. `attach` creates a valid digest identity once and a later attach reads the
   same identity after the repository directory is moved.
2. No Core API introduces a global current repository, Work Item, or profile;
   repository-bound CLI/MCP operations continue to require explicit context.
3. Architecture, Runtime topology, configuration, and user entry documents in
   English, Chinese, and Japanese show one shared Runtime with isolated
   Repository Contexts.
4. Hosted quality tests do not run process-spawning package binaries
   concurrently; V1 Oracle and Windows runtime checks remain required.

## Required Evidence

Focused attach/move, repository receipt, verification-service, CLI, Clippy,
format, diff, hosted quality, Windows runtime, and V1 Oracle results.
