# WI-38 — 只生成治理脚手架，不生成治理决定

## Intent 与 Goal

在不引入治理决定的前提下提供治理脚手架。Rust Core 仍是工程外部共享且无项目持久状态的
Runtime；每个显式绑定的 repository 只得到可确定推导、可被验证器读取的最小骨架。

## Scope 与 Out of Scope

范围：最小 `attach` 脚手架、repository 本地 discovery manifest、`work-item new`、与过渡期
`start` 共用的 contract scaffold API、默认只读的 `profile propose`、隔离测试和三语用户文档。
不在范围：Agent provider 注入、全局 MCP 修改、自动生成 authority/intent/acceptance、正式 profile
baseline 应用，以及业务工程模板。

## 硬约束

- `attach` 只创建协议状态与 repository identity，不修改 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`、
  `.cursor/**` 或用户全局 MCP 配置。
- `work-item new` 只能填充由当前 snapshot 确定推导的事实；intent、scope、acceptance criteria、
  authority 必须保持空值或 `unknown`。
- 骨架状态必须是 `not_ready`/`unknown`，不能声称 `passed`、`approved`、`verified` 或 `completed`。
- `profile propose` 必须标记为 candidate/proposed，且没有独立的显式 apply 流程就不能修改正式 baseline
  的 bytes 或 digest。
- 所有 CLI 命令都必须显式提供 `--repo`，不得引入进程级 current project 状态。

## 验收标准

1. 重复执行 attach 结果字节稳定，不产生无意义 diff。
2. A/B 两个 repository 并行 attach 与创建 Work Item 时，ID、snapshot、profile、Contract、evidence
   完全隔离。
3. `work-item new` 自动填充 `repositoryId`、`baseRevision`、`projectProfileDigest`、
   `repositorySnapshotDigest`。
4. 不推断人类字段，现有验证器保持 not-ready。
5. profile proposal 不改变正式 profile，并明确标记 candidate/proposed。
6. 不写入 provider 文件或全局 Agent 配置。
7. 英文、中文、日文文档说明同一边界，并列出命令输出中的缺失人类输入。

## Required Evidence

repository/protocol/CLI focused tests、并行隔离测试、profile baseline 字节对比、format、Clippy、diff、
全 package tests，以及文档一致性和可读性复核。
