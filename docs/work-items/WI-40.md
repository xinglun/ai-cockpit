# WI-40 — Post-release Adopter Acceptance Baseline

## Intent and Goal

Establish a reproducible post-release adopter acceptance baseline using only
immutable public Release artifacts. The baseline must prove that a real
GitHub Release binary can govern a fresh adopter repository from zero, while
preserving an auditable receipt when post-release acceptance fails.

## Scope and Out of Scope

In scope: `tests/release/adopter_acceptance.sh`; its immutable Release download
and digest checks; isolated HOME/XDG/TMP/Cargo/adopter setup; attach/profile/
Agent/doctor/verify evidence; `first-adopter-smoke` not-ready assertions; a
complete Work Item lifecycle; before/after evidence reuse; `acceptance.json`;
directory `SHA256SUMS`; post-publication `adopter_acceptance` CI; and
English/Chinese/Japanese documentation.

Out of scope: a Runtime `acceptance` command; source or Protocol changes;
global Agent/MCP configuration; pre-publication gating; changing existing
Release truth; and a second technology-stack adopter.

## Hard Constraints

- The harness never uses `cargo build`, `cargo run`, a workspace binary, or a
  local `target` binary to obtain AI Cockpit.
- Every Runtime call uses the absolute downloaded binary whose digest is in
  `runtime.json`.
- `runtime.json` binds tag, version, archive digest, binary digest, platform,
  archive, download source, and public Release state.
- `acceptance.json` retains `releasePublished: true` when adopter acceptance
  fails; a failed receipt cannot authorize a later version.
- `SHA256SUMS` covers every emitted evidence file except itself.
- Each run has isolated HOME, XDG_CONFIG_HOME, TMPDIR, CARGO_HOME, and adopter
  repository paths.
- `first-adopter-smoke` stays `not_ready`; intent, scope, acceptance criteria,
  and authority are never invented.

## Acceptance Criteria

1. The script downloads only the requested immutable public Release archive,
   manifest, and checksum, and rejects version/tag/digest mismatch or any
   source fallback.
2. Runtime version and binary digest match `runtime.json`, `doctor`, `inspect`,
   and Work Item verification evidence.
3. A fresh adopter receives a distinct repositoryId and passes attach, profile
   confirmation, Agent adapter installation, and `VERIFIED` doctor.
4. The `first-adopter-smoke` contract is preserved as `not_ready` with all
   human-owned fields empty or `unknown`.
5. A separate Work Item produces start, checkpoint, preflight, verify, finish,
   archive, close, outcome, and verification evidence.
6. Two identical sanitized verify invocations show first execution and second
   receipt reuse with zero spawned processes on the second run.
7. Source checkout `.ai/` is absent and HOME/XDG before/after manifests are
   identical.
8. `acceptance.json` summarizes every step and `SHA256SUMS` binds the complete
   evidence directory.
9. The release workflow runs this harness only after `publish` and
   `publish_handoff`, uploads evidence on both success and failure, and never
   rewrites the already-published Release.
10. English, Chinese, and Japanese docs describe the same post-release boundary.

## Required Evidence

The acceptance artifact must include `release.json`, `runtime.json`,
`repository.json`, `attach.json`, `profile-confirm.json`, Agent list/install/
doctor JSON, first and reused verify JSON, isolation JSON, the not-ready
contract, every lifecycle receipt, `acceptance.json`, and `SHA256SUMS`.
