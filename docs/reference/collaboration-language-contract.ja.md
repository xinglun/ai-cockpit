# 協作言語契約

[English](collaboration-language-contract.md) · [简体中文](collaboration-language-contract.zh-CN.md)

North Star: Calibrated Human-Agent Trust（較正可能な人間-Agent 信頼）。維持管理者にその場で説明を求められない新規ユーザーでも、各協作の節目で Agent が何を述べているかを読み取り、現在の Runtime 状態を理解し、境界の明確な決定を下し、別の Agent やセッションに引き継いだ後もその理解を失わないようにする。

## 本契約が何であり、何でないか

本ページは**地図**であり、新しいプロトコルではない。新しい状態、マーカー、終了コード、ライフサイクルコマンドを定義せず、既存のいかなる意味も変更しない。以下に挙げる事実にはすべて、唯一の権威ある出典が既に存在する：[`.ai/glossary.md`](../../.ai/glossary.md)、[Repository Protocol 仕様](../protocol/v1/specification.md)、[人間向け Outcome](outcome-report.md)、[Cockpit Status の読み方](how-to-read-cockpit-status.md)、[Agent ワークフローとレビュー境界](agent-workflow.md)、[トラブルシューティングと復旧](troubleshooting.md)。本ページによるある協作節目の言い換えが出典文書と食い違う場合は出典文書を正とする。本ページはそれらへの索引として読むべきであり、代替物ではない。

本ページの内容は、まだ `main` にマージされていない性能専項の文書（`docs/reference/performance-initiative-2026-09.*`、未マージの WI-651 後継チェーンが保持）およびアーキテクチャ専項の文書（`docs/reference/architecture-responsibility-map-2026-09.*`、未マージの WI-652 後継チェーンが保持）のいずれとも矛盾しない。ここでの言及はマージ後の将来的な相互参照のためだけであり、本契約はそれらの内容に依存せず、それらのドラフトブランチを権威あるものとして扱わない。

## すべての引き継ぎが答えられるべき五つの問い

表現言語、CLI/MCP のどの入口か、あるいはどの Agent やモデルが発話しているかにかかわらず、決定や結果を人に引き渡す協作節目は、読者がその場の発話だけから（以前の会話の記憶に頼らずに）次の五つすべてに答えられるようにしなければならない。

1. **現在どのような状態にあるか？**——`status --repo <repo> [--id <work-item>]`、現在の Summary の `state`、および/または `work-item outcome` に由来する。
2. **どの事実が確認済みで、どれが未知か？**——`unknown` フィールドはそれ自体が一つの事実であり、「たぶん問題ない」の代替表現ではない。[人間向け Outcome § ステータスマーカー](outcome-report.md)を参照。
3. **人による決定が必要か、その理由は何か？**——`preflight` の `reviewState`、および `needs_human_confirmation` の場合に付随する構造化された `humanDecisionRequest`（何が起きたか、なぜ重要か、選択肢、推奨、問いそのもの、再開条件）に由来する。[Agent ワークフロー](agent-workflow.md)を参照。
4. **各選択肢は実際に何をし、その授権範囲はどこまでか？**——ある選択肢の効果は、それが呼び出す Runtime コマンドの効果そのものである（例：一度の checkpoint 遷移を解錠する。テスト・シナリオ・検証・リリースのいずれの結果も証明しない）。どの選択肢も、それが引き起こすコマンドより広い言葉で説明してはならない。
5. **決定後どこへ進み、どの条件で再び停止するか？**——次の action とその再開条件は、Outcome の `next action` フィールドまたは Preflight Review から一字一句取得するものであり、創作してはならない。

事実が前回から変わっていない場合、応答はこれらの一部を圧縮または省略してよいが（固定見出しを毎回繰り返す必要がない理由については[多言語意味的整合性](multilingual-semantic-parity.md)を参照）、省略によってこの五つのいずれかが答えられなくなることは決してあってはならない。

## 協作の節目

以下の各節目は、Agent が何かを人に引き渡す瞬間である。各節目について、トリガーと事実の出典、ユーザーが理解すべき状態、Agent が示すべき情報、人による決定が必要か、各選択肢が実際に授権する範囲、決定後の次の一歩と再び停止する境界、そして情報の欠落・誤解・取消への対処を示す。

### 1. タスク開始と範囲確認

- **トリガー/事実の出典**：`work-item new --mode <mode>` によるスケルトン生成、または `start --intent --goal [--scope] [--out-of-scope]`；その結果生じる Contract の `state` と `preflight` の `reviewState`。
- **理解すべき状態**：`intent`、`goal`、`scope`、`out-of-scope`、`acceptanceCriteria`、`authority` のいずれかが空のスケルトンは、明示的に `not_ready` / `needs_human_confirmation` であり、終了コードにかかわらず「実装してよい」を意味したことは一度もない。
- **示すべき情報**：Runtime が既に解決済みの事実（`repositoryId`、`baseRevision`、各種ダイジェスト）と、まだ空である人間所有フィールドとの対比；発見された remote のデフォルトブランチと base revision。
- **人による決定が必要か**：常に必要——実装前に intent/scope/acceptance/authority を与えること自体がその決定であり、暗黙のデフォルト値は存在しない。
- **各選択肢とその範囲**：scope のみを与えても、それは編集の境界を縛るだけで、risk・authority・acceptance を与えない。各フィールドは独立しており、他のフィールドから推測できない。
- **次の一歩/停止境界**：`work-item new` または `start` が成功すると `preflight` に進む；`not_ready` または `needs_human_confirmation` という preflight の結果はそこで停止し、Contract が修正されるまで動かない——成功を示す助言的な終了コードは実装の許可ではない。
- **欠落/誤解/取消への対処**：空または曖昧なフィールドは `unknown` のままにし、ファイル名・自然文・過去のセッションから推測しない。人は Work Item を `not_ready` のままにすることで取消できる——`start` が成功するまで片付けの義務は生じない。

### 2. 授権請求

- **トリガー/事実の出典**：`humanDecisionRequest` を伴う `needs_human_confirmation` を返す `preflight`；有界なレビューを記録するリポジトリローカルの `decisionEvidence` 投影。
- **理解すべき状態**：一つの授権請求は、一つの Contract ダイジェストと一つのリポジトリスナップショットダイジェストの組み合わせにのみ及ぶものであり、両者の将来の変化に対する恒常的な承認ではない。
- **示すべき情報**：何が起きたか、なぜ重要か、選択肢、推奨、問いそのもの、再開条件——この四つの構造化フィールドをすべて示すべきであり、要約文一つで代替してはならない。
- **人による決定が必要か**：必要である。成功したコマンドや黄色の結果それ自体が授権になることは決してない（[`.ai/glossary.md`](../../.ai/glossary.md) の Pause Rule を参照）。
- **各選択肢とその範囲**：記録された決定の受領票は `decisionId`、Work Item、リポジトリ、Contract ダイジェスト、preflight 決定ダイジェスト、スナップショットダイジェスト、行為者、タイムスタンプ、理由を束縛する；それが解錠できるのは名指しされた一度の checkpoint 遷移のみであり、テスト結果・検証結果・リリース決定のいずれも証明しない。
- **既存授権の再利用 vs. 新規授権の請求 vs. 純粋な技術的復旧**——これらは三つの異なる事柄であり、混同してはならない：
  - *再利用*は、Receipt の身分束縛（リポジトリ、Work Item、Contract ダイジェスト、スナップショットダイジェスト、Runtime の身分）が依然として一致する場合にのみ成立する。再利用は規則と記録の一致であり、「同じ依頼のように見える」という自然言語による推測では決してない。
  - 以前のレビュー後に Contract またはリポジトリスナップショットが変化した場合は*新規授権*が必要である。以前の受領票は歴史的証拠として保持され、新しい受領票はダイジェスト付きの別パスに書き込まれる。
  - *純粋な技術的復旧*（`work-item recover` の `retry`、`successor`、`supersede`）は新しい授権を一切与えず、ブロックまたは赤の結果を緑に変えることも決してない。合法なライフサイクル位置を復元し、新しい `verify`/`finish` を実行できるようにするだけである。
- **次の一歩/停止境界**：有効な決定が解錠するのは、それが名指しした一度の checkpoint 遷移のみ；Work Item は `finish` の前に依然として新しい `verify` を必要とする。
- **欠落/誤解/取消への対処**：欠落・陳腐化・出所不明・形式不正な受領票は停止状態を維持する；授権を拒否した場合、Work Item は現在の安全な状態にとどまり、強制的な再試行は発生しない。

### 3. 検証の合格・失敗・証拠不足

- **トリガー/事実の出典**：`verify --repo <repo> --id <id>`；`.ai/evidence/` に書き込まれる受領票；Outcome 内の独立した Verification ステータス行。
- **理解すべき状態**：**検証の合格は、合併の授権・リリースの授権・全面的な受け入れとは別の事実である。** Outcome は意図的に Verification、Lifecycle、Human decision、Governance signal を四つの独立した行として保持している；緑色の Verification 行が意味するのは、宣言された各チェックが新鮮で身分束縛された受領票の上で合格したという事実のみである。
- **示すべき情報**：どの宣言済みチェックがどのスナップショット上で実行されたか、そしてその結果の決定状態の色；証拠が現在のものか、旧式（`legacy_evidence_historical`）か、歴史的だが未再検証（`historical_evidence_not_revalidated`）か——[人間向け Outcome](outcome-report.md)を参照。
- **人による決定が必要か**：通常の緑の結果には不要（自らのプロセスに従って名指しされた証拠を確認して進めればよい）；黄色には必要（調査または確認）；赤は常に停止を要する。
- **各選択肢とその範囲**：緑色の Verification 行を越えて進むことが授権するのは、そこに列挙された宣言済みチェックのみであり、合併・リリース・セキュリティ声明とは無関係である。黄色の結果は、無関係なコマンドを再実行しても修復されない。
- **次の一歩/停止境界**：緑は `finish` に向けて進む；黄色は `finish` の前に調査または明示的な決定を要する；赤は停止し、名指しされた復旧条件を満たす必要がある。
- **欠落/誤解/取消への対処**：取消または中断された検証は受領票を残さず、Work Item は以前のライフサイクル状態にとどまる；再試行は常に安全であり、一致しない受領票を静かに再利用することは決してない。

### 4. 阻断と復旧

- **トリガー/事実の出典**：阻断された `finish`（または `checkpoint`）は赤/黄の Outcome を永続化し、元の非ゼロエラーを返す；明示的なライフサイクル復旧には `work-item recover` を用いる。
- **理解すべき状態**：阻断された Work Item は checkpoint 済みのライフサイクル状態を保持する；阻断は Runtime が投影した Outcome として可視化され、静かに握りつぶされた失敗ではない。
- **示すべき情報**：失敗したゲート、決定論的な復旧条件、そして意図されている次の行動が単純な再試行（同じ Contract、同じ範囲）か復旧決定（`retry`/`successor`/`supersede`）かのいずれであるか。
- **人による決定が必要か**：名指しされた原因を修正した後の単純な再試行には新たな授権請求は不要である；`successor` または `supersede` の決定は、範囲・権限・base を変更するか、前身を歴史的なものと宣言するため、新しい明示的な、記録される決定である。
- **各選択肢とその範囲**：`retry` は合法な `checkpointed` の位置を復元して一度の新しい検証試行を可能にするだけで、以前の阻断イベントを書き換えない；`supersede` は前身の元のバイトと証拠を歴史として保持する——それは現在の合格でも現在の失敗でもない。
- **次の一歩/停止境界**：再試行が成功した後は、新しい `verify` と `finish` が次の現在の Outcome を生成しなければならない；阻断されたイベントは監査のために追記専用のイベントストリームに残る。
- **欠落/誤解/取消への対処**：曖昧・出所不明・改ざんされた復旧候補は `recovery_decision_invalid` として拒否され、何も変更しない；復旧しないという選択は Work Item を阻断状態のまま残すが、それ自体が安全で検査可能な状態である。

### 5. 合併確認

- **トリガー/事実の出典**：ホスト側のチェックに合格したレビュー済み Pull Request；`work-item finalize-plan` → `finalize` → `finalize-verify` → `close`。
- **理解すべき状態**：**合併は Work Item の終結ではない。** マージされた PR が開始するのはリソース終結という別の境界にすぎず、ブランチ/worktree の片付け、`Deleted` の終結受領票、確認済みの `close` 決定はすべて依然として必要であり、リポジトリ検証とは別の境界である。
- **示すべき情報**：マージされた PR の head SHA、デフォルトブランチが同期済みかどうか、そして正確な残りの手順（ブランチ/worktree の片付け → 終結受領票 → `finalize-verify` → `close`）。
- **人による決定が必要か**：`close` には必要であり、明示的な `--human-decision` を要する；`Retained` の終結受領票は中間観察または明示的な歴史的事実にすぎず、それ単独で `close` を授権することは決してない。
- **各選択肢とその範囲**：PR の承認は合併そのものを授権するだけであり、片付けの省略を授権せず、それ自体で `close` を授権せず、ローカル検証を遡ってホストまたはエンタープライズ級の保証に格上げすることもない（[Cockpit Status の読み方 § 証拠の境界](how-to-read-cockpit-status.md)を参照）。
- **次の一歩/停止境界**：`close` の後、確認済みの close 決定が有効な場合にのみライフサイクル投影は `closed` になる；無効または欠落した決定は、アーカイブ状態を `closed` に昇格させることは決してない。
- **欠落/誤解/取消への対処**：プロバイダのエラー、身分の不一致、不完全な終結観察は `unknown` として扱われ、Work Item は復旧のために開かれたままとなる——次の Work Item に進んでよいという許可として扱われることは決してない。

### 6. Outcome

- **トリガー/事実の出典**：`work-item outcome --repo <repo> --id <id>`（CLI）、または明示的な `workItemId` を伴うリポジトリ束縛の MCP `work_item_outcome` ツール。
- **理解すべき状態**：Outcome は終端の可視な引き渡しであり、折りたたまれたログ行や生の `work_item_get` の機械記録がその代わりになることは決してない。完全なフィールド順序、マーカーの意味、証拠の規則は[人間向け Outcome](outcome-report.md)で一度定義されており、ここでは繰り返さない。
- **示すべき情報**：`Outcome: 🟢/🟡/🔴` マーカーと、読者優先の順序で生成された全内容（タスク結果、完了した作業、発見された問題、発動した停止、解決された問題、リスク、未知事項、人による決定、検証と証拠、影響、次の action）——Agent はいずれの節も並べ替え・折りたたみ・省略してはならない。
- **人による決定が必要か**：マーカーによる；Outcome 自体が保留中の決定の有無とその内容を述べる。
- **各選択肢とその範囲**：Outcome 自体は新しい選択肢を導入しない；事実とすでに記録された決定（もしあれば）を報告するのみである。
- **次の一歩/停止境界**：`next action` フィールドが述べる内容そのもの。
- **欠落/誤解/取消への対処**：空の節は「未記録」または「未評価」として表示され、決して肯定的な事実としては表示されない；読者が緑の Verification 行をリリース完了と誤解した場合、正しい訂正方法は Outcome の文言を変えることではなく、四つに分離されたステータス行へ改めて注意を向けさせることである。

### 7. Agent またはセッションの引き継ぎ

- **トリガー/事実の出典**：同じリポジトリ・同じ Work Item に対して、新しい Agent、新しい会話、あるいは異なる基盤モデルが作業を再開すること。
- **理解すべき状態**：上記の各節目が述べる内容はすべて、会話の記録に一切頼ることなく、Runtime のみ——`status`、`work-item outcome`、現行/アーカイブ済みの Contract、Summary、決定記録——から再導出できるべきである。「引き継ぎ状態」を一度の呼び出しにまとめる専用の Runtime コマンドは現時点で存在しない；引き継ぐ Agent は上記と同じ `status`/`outcome`/Contract/Summary の出典から自分でそれを組み立てる。
- **示すべき情報**：現在の目標と範囲の境界（Contract）；完了済みと未完了の事項（Summary の `state`、`checkpointCount`）；どの証拠が有効でその適用範囲はどこか（`.ai/evidence/` と鮮度の束縛）；どの授権が記録済みでどの決定が未決か（`decisionEvidence`、`humanDecisionRequest`）；阻断されている場合はその理由と合法な次の一歩（永続化された Outcome）。
- **人による決定が必要か**：引き継ぎ以前から既に未決の決定があった場合のみ必要；引き継ぎ自体が新しい決定点を作り出すことは決してなく、古い決定点を静かに解消することも決してない。
- **各選択肢とその範囲**：引き継ぎ自体はいかなる選択肢も作り出さない。
- **次の一歩/停止境界**：引き継ぎ以前と全く同じ；新しい Agent が引き継ぐのは同じ停止境界であり、新しい境界ではない。
- **欠落/誤解/取消への対処**：ある事実が Runtime から復元できない場合、それは人による回答を要する明示的な欠落として提示しなければならず、新しい Agent 自身の癖、特定のモデルに特有の言い回し、あるいは提供されていない過去の会話から推測してはならない。セッションの切り替えによって、記録済みの授権が静かに「まだ付与されていない」に戻されてはならず、範囲の定まった授権が、それが一度も名指ししていない新しい範囲へ静かに広げられてもならない。既存の授権が今も適用されるかどうかは、第2節に述べた身分束縛の規則によって決まるのであり、現在どの Agent が発話しているかによっては決まらない。

## 十の意味論的不変量

以下は、上記の出典が既に記載している保証を、検査可能な規則として言い換えたものである。いずれも新しい統治規則ではない；それぞれについて、今日どこで既に成立しているか、そして（該当する場合）どの後続 Work Item が自動チェックを追加する予定かを示す。明示されない限り、自動化されたカバレッジは現時点でまだ存在しない；[現在の未知事項と後続作業](#現在の未知事項と後続作業)を参照。

1. **検証の合格それ自体は、全面的な受け入れや合併の授権を意味しない。** 既に記載済み：[人間向け Outcome](outcome-report.md)（「緑色の結果は、合併・リリース・公開・セキュリティ声明のいずれも授権しない。」）。
2. **空の記録は、リスクが存在しないことを意味しない。** 既に記載済み：空の節は「未記録」/「未評価」として表示され、決して肯定的な発見としては扱われない（[人間向け Outcome](outcome-report.md)）。
3. **未知の事実は、表現層によって補完されてはならない。** 既に記載済み：`unknown` の証拠は決して合格として解釈されない（[`.ai/glossary.md`](../../.ai/glossary.md)、[Decision states](../protocol/v1/specification.md)）。
4. **歴史的な記録は、明示的な根拠なしに現在の失敗や現在の有効な証明に変わってはならない。** 既に記載済み：取って代わられた証拠および歴史的な証拠は黄色の歴史マーカーとして投影され、現在の結果として静かに再検証されることは決してない（[人間向け Outcome § 歴史マーカー](outcome-report.md)）。
5. **同一の事実は、CLI・MCP・要約・完全なレポートのいずれで表現しても矛盾してはならない。** 設計意図としては[多言語意味的整合性](multilingual-semantic-parity.md)および[人間向け Outcome](outcome-report.md)の MCP の節（`work_item_outcome` は CLI が出力するのと同じローカライズされた引き渡し内容を返す）に既に記載されている；ただし入口をまたいだ構造的な自動チェックはまだ構築されていない——後続作業として位置付ける。
6. **言語を変更しても、事実・授権範囲・操作上の帰結は変わらない。** 既に記載済み：[多言語意味的整合性](multilingual-semantic-parity.md)——JSON のフィールド名と列挙値は安定しており、Contract が所有するテキストは機械翻訳されない。
7. **表示される次の一歩は、現在の Runtime 状態と方針に一致しなければならない。** 既に記載済み：次の action は Outcome または Preflight Review から取得され、決して創作されない（「レポートは統治上の決定を推測によって埋めることは決してない。」——[人間向け Outcome](outcome-report.md)）。
8. **既存の授権が適用されるかどうかは規則と記録によって決まり、セッションの切り替えによって恣意的に破棄・拡大されてはならない。** Receipt について既に記載済み（[`.ai/glossary.md`](../../.ai/glossary.md)：「すべての授権済み身分束縛が依然として一致する場合にのみ再利用できる」）；[第7節](#7-agent-またはセッションの引き継ぎ)で Agent/セッションの引き継ぎに適用した。模擬的なセッション切り替えを対象とした専用の引き継ぎ継続性チェックはまだ構築されていない——後続作業として位置付ける。
9. **人による決定を要するすべての問いは、決定の対象、影響、復旧/再開条件を明示しなければならない。** 既に記載済み：構造化された `humanDecisionRequest` の形（[Agent ワークフロー](agent-workflow.md)）。
10. **要約は詳細を省略してよいが、阻断・重要な未知事項・必要な人による決定を隠してはならない。** 既に記載済み：`--json` が stderr 上の人間可読な形式を抑制している場合でも、阻断された `finish` は永続化された赤/黄の Outcome を出力し続ける；未知事項も圧縮によって取り除かれることはない（[人間向け Outcome](outcome-report.md)）。

## 現在の未知事項と後続作業

本文書は、文書としての構造的チェック（frontmatter の完全性、内部リンクの解決可能性、三言語の揃い）と、維持管理者/レビュアーによる読解によってのみ検証される、文書のみの成果物である。**自動化された意味的チェックによっては検証されておらず**、いかなるユーザー調査によっても検証されていない。上記の不変量のすべてが今日すでに入口をまたいだ自動強制を備えていると主張するものではない；いくつかは明示的にまだ備えていない（不変量5と8を参照）。以下は本 Work Item に統合するのではなく、別個の後続 Work Item として位置付ける：

- 合法な遷移と不正な遷移、証拠の欠陥、既存授権の再利用と新規授権の区別、検証結果、アーカイブ/クローズ/代替/歴史照会、そして言語と入口をまたいだ Agent/セッションの引き継ぎを網羅する、状態と遷移から生成されるシナリオ行列。
- 上記十の不変量それぞれについて、正例・反例・境界事例を備え、固定文字列の一致ではなく、制御されたテストリポジトリ上で実行される自動チェック。
- 制御されたテストリポジトリにおいて、表示された状態、選ばれた選択肢、実際の Runtime の振る舞いの三者が一致すること（中断と再開を含む）をエンドツーエンドで検証すること；このために用いる模擬的な人による決定はすべてテストデータとして明示し、実際の授権記録になることは決してあってはならない。
- 新しい Agent またはセッションが、会話記録に頼ることなく Runtime のみから目標/範囲、完了済み/未完了事項、有効な証拠とその適用範囲、有効な授権と未決の決定、阻断理由を再構築できることを確認する引き継ぎ完全性チェック。

本文書が現在カバーしている範囲において、これは引用した出典に根ざした、一貫性があり追跡可能な交流の意味論を目指すものである。すべての読者が正しく理解することを主張するものではない。その主張には、本 Work Item が行っていない観察的検証が必要となる。
