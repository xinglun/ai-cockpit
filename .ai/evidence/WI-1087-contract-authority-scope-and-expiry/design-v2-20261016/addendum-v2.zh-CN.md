# WI-1087 设计 v2 补充：撤销、提交、版本与期限

2026-10-16（Asia/Tokyo）。Raydot 通过规划方向，当前用户要求补清四个边界。此为 **planning/not_ready 的版本化设计补充**，产品实施 authority 仍为 missing；没有真实 grant 配置、Runtime 激活、checkpoint、构建或产品验证。v1 字节保持原样；本文件与 v1 共同构成当前设计，以下精确定义收窄 v1 中“版本取代/授权终止/更早期限”的泛称。

## 1. 撤销与提交的并发边界

仅“拿锁后检查一次再解锁”不足以保证撤销：检查与实际效果间仍有竞态。复用现有锁/事务与来源 head 的 expected-version/CAS，在**实际效果提交或外部请求开始分发**的边界重查；不新增平行的批准数据库。锁顺序与现有 WI/resource 锁一致，授权来源锁只覆盖有界的最终判定/本地提交；撤销写入不等待被撤销的长任务完成，不持授权锁等待整个外部网络操作。

| 可证明的排序 | 必需行为与证据 |
| --- | --- |
| 本地原子提交与撤销使用同一个可排序的来源屏障；撤销先提交 | 重新读取当前 sourceVersion/终止状态后拒绝效果，effectCount=0；旧 admission/已准备输出不形成提交权。 |
| 本地效果在屏障内先提交，随后撤销提交 | 保留该已完成的合法历史；撤销之后不允许下一业务步骤。提交回执与撤销序号记录真实顺序，不倒填时间。 |
| 同目标延期/版本替换与撤销并发 | 更新当前 source head 的写入串行/CAS；撤销针对稳定 grant/subject，不能被合法版本替换丢掉。若延期先提交，撤销仍须作用当前同一 grant；若撤销先提交，延期不得清除终止标记或复活。CAS 冲突不是成功撤销，回执必须如实报告，不能提前宣称已停。 |
| 外部动作尚未分发，撤销先完成 | 即使先前已准备/缓存批准，也拒绝分发；不得凭预留 receipt 延长有效性。 |
| 外部请求已实际分发，之后撤销完成 | 这是在途动作。取消/补偿只按原先明确的安全策略和独立权限执行；外部结果可能稍后到达，保留真实效果/未知状态。 |

外部 Provider 支持条件版本/fencing token 或事务时，把适用来源版本/操作身份绑定到其可校验条件；普通本地锁不等于跨系统原子性。Provider 不支持撤销屏障时，不能保证“撤销提交后外部绝不产生此前已分发动作的效果”。要求这种强保证的操作应报告 unsupported 并在分发前停止；只在授权已明确接受有界在途语义时采用在途方案。不能把本地 dispatch receipt 当成外部 commit 回执。

屏障不暂停时间流逝：在真正 effect/dispatch 边界重新用 Clock 检查 notBefore <= now < expiresAt，剩余预算不能由已准备、拿过锁、排队或来源版本更新自动延长。先前未发生的业务步骤在撤销/到期后不得继续。并发验收使用可控 Clock 与显式 barrier，按两种顺序分别断言，无长 sleep。

## 2. 版本替换与授权终止

区分三种身份/状态，不再用一个 superseded 同时表示：

- **sourceVersion 被新版本取代**：同一稳定 grantId/goalRef 的不可变版本历史。正常已批准的同目标期限调整可产生当前新版本；旧版本不再授权新动作，旧回执与当时合法结果仍是历史。版本更新本身不等于目标完成、撤销或 WI 关闭；适用的活跃 WI 在下次准入统一解析当前版本。
- **当前执行窗口失效**：notBefore 尚未到、expiresAt 到期或来源当前不具执行效力时禁止业务。单纯时窗届满后，未完成目标若允许正式延期，必须由有权授权者显式批准新的未来窗口/来源版本；空档期零业务效果，不追认空档执行。该明确决定不自动修改 WI 固定更早截止。
- **grant/目标被明确终止或 WI 被关闭、撤销、正式取代**：稳定主体的终止事实是独立且不可被普通期限版本替换清除的记录。完成/撤销/正式终止的 grant 不可被延期复活；closed/revoked/superseded WI 不因 sourceVersion 更新重新进入执行。确有后续新授权需求须采用正常新来源/新主体决定，保留前驱历史。

因此 v1 中“到期终止后续执行”仍严格成立；同目标已批准的新未来窗口不是把旧过期窗口变为一直有效。v1 中“superseded 不复活”针对被正式取代的 WI/授权主体，不把普通 sourceVersion 的历史替换误当整个 grant 的永久终止。新的目标 B 仍不能引用 A 的版本更新获得授权。若版本更新夹带 actor/action/resource 扩张或排除项变化，独立范围决定仍必需。

撤销记录必须绑定稳定 grant/subject 和真实撤销者权限及实际来源版本观察；并发版本变化不能用来丢弃已接受的撤销。成功响应仅在终止事实耐久提交后返回；失败/冲突/未知要保留实际状态。所有后续版本解析与动作准入都检查终止事实，不能仅检查当前版本 digest 或 expiresAt。

## 3. 继承期限与固定更早期限

目标来源始终有明确有限 expiresAt；WI 引用需明确 deadline mode。WI 不声明固定 cap 时只能表达“继承有限当前来源及父链”，不能被解释为无限授权，也不能把最初复制的 expiresAt 错当固定 cap。

| WI/子委托声明 | 计算规则 | 同目标合法 source 延期之后 |
| --- | --- | --- |
| inherit_source | effectiveEnd = min(当前 source.expiresAt, 当前父链有效截止, 其他现有有限限制) | 在下一次新鲜准入中跟随来源/父链变化；同目标已覆盖活跃 WI 无逐项再批准。 |
| cap_at(固定绝对 UTC 截止) | effectiveEnd = min(继承结果, 明确 cap_at) | cap_at 保持原值，不自动增大。要延长该更窄限制，需要对应授权者的正式变更。 |

生效起点取 source、父链与 WI 明确更晚 notBefore 的最大值。子委托不能越过父链 actor、scope、action/resource 或期限；创建时伪报超父的明确期限拒绝，继承不是另造一份独立授权。当前 source 缩短期限时，两种 mode 都立即收窄；WI 固定 cap 可能比新 source 更早，始终取更严者。对一次在途操作还取已有单操作 deadline/monotonic budget 的最小值，来源延期不能静默重置正在运行操作的预算。

示例仅为验收：来源原截止 18:00，新版本延期到 20:00。B 为 inherit_source，未来新动作可计算至 20:00；C 明确 cap_at 17:30，仍在 17:30 停止。若父委托固定截止 19:00，继承它的子 WI 最晚仍是 19:00。所有时间示例不配置真实授权。

## 4. 在途撤销的停止行为

撤销耐久生效后，Runtime 立即拒绝新的受管 admission、业务子步骤、retry/recovery 和不可逆提交，并使本地缓存/旧许可不能继续执行。在途监督器通过现有受管事件/安全点观察撤销，不承诺任意外部 agent 的瞬时停止；监控延迟及停止能力是明确的 assurance/结果字段，能力不足报告 unknown/unsupported。

| 在途类型 | 撤销后的允许行为 | 禁止推断 |
| --- | --- | --- |
| 可取消的本地受管进程/事务 | 仅停止自身已启动进程、执行事先授权的有界一致性策略、保全已捕获输出；记录 cancel requested/observed exit/reap 的真实结果。 | 发过信号不等于已停止，不批量 kill，不自动删除资源。 |
| 正在运行且必须到安全点的步骤 | 到下一受管安全点停止；停止路径本身要有预声明的有限预算和最小权限。 | 不借“安全收尾”开始新业务读取、导出、提交或补偿。 |
| 已分发且不可撤回的外部事务 | 按既有明确权限尝试取消；接受稍后返回的实际 receipt/已捕获输出，保留 late completion、effect unknown 或 cancellation unknown。 | 不伪造 rollback、无效果或 stopped；新业务查询/外部补偿仍需其自身有效权限。 |

撤销后最小 metadata 管理面仍可保全已捕获证据、查看本 WI/授权状态、报告真实停止/未知并提交新请求，不可借它重新扫描业务 source/material 或清理外部资源。目标完成/到期适用同样的后续业务禁止和真实历史保留原则；已有不可逆效果不会被撤销决定从历史中抹去。
